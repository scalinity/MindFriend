# Support chat wire contract (M4, schema_version 1)

Server: `supabase/functions/chat/index.ts` + `supabase/functions/_shared/support-chat.ts`.
Spec: `docs/SUPPORT_SESSION_SPEC.md` 8.2-8.6, 9.7, 10.1. Samples: `artifacts/support-session/m4-fixtures/*.json`
(generated by `supabase/tests/support_chat_test.ts`; ids and times normalized).

Nothing here starts, completes or schedules anything. A `proposal` is data. The person must explicitly accept it
through `support-session` (`accept_proposal` with `proposal.id`).

## 1. Negotiation (the client MUST fail closed)

The server cannot tell a new client that forgot a field from an old client, so **the client proves the deployed
chat function first**:

```
POST /functions/v1/chat            (same auth as chat)
{"op":"capabilities","schema_version":1}
```

200 body (all keys come from the database `support_capabilities()` plus the chat function's own marker):

```json
{"ok":true,"op":"capabilities","chat_contract":1,"session_contract":1,"context_policy":1,"voice_context":0,
 "privacy_revision":true,"memory_lifecycle":true,"chat_confirmation":true,"lazy_attach":true,
 "schema":"20261106230200","status":"ok"}
```

- Support SQL not deployed: HTTP 200 with `status:"not_deployed"`, `session_contract:0`, `context_policy:0`.
- Transient error: HTTP 503 `code:"chat_support_unavailable"`, `capability:"unavailable"`, `retryable:true`.
- A chat function that predates this contract answers `{"op":"capabilities"}` with **400** (no provider work). Treat any
  non-200, a missing `chat_contract`, or `chat_contract < 1` as **unsupported**.
- Required to send privacy-bearing chat: `chat_contract >= 1`, `context_policy >= 1`, `privacy_revision == true`,
  `chat_confirmation == true`, and `session_contract >= 1` when a `support_session_id` is sent.
- Unsupported/unavailable: pause cloud chat, keep the draft and local practices, show the honest unavailable state.
  **Never** resend as a legacy-shaped request (no new fields): the old path uses the old personal-context policy.
- `session_contract`, `context_policy`, `voice_context` are separate numbers. This slice uses the first two.
- The handshake consumes one slot of the 10/minute chat rate limit. Do it per launch/account epoch and after a
  `chat_support_unavailable`, not per message.

## 2. Request

`POST /functions/v1/chat`, `Authorization: Bearer <jwt>`, `Content-Type: application/json`,
optional `Accept: text/event-stream`.

Existing keys are unchanged: `conversationId`, `content` (trimmed, 1-4,000 chars), `requestId` (UUID),
`retryFailed` (bool). New keys (**any one of them present makes this a new-contract request**):

| key | type | rule |
|---|---|---|
| `schema_version` | integer | must be `1`; anything else is 400 `chat_support_schema_unsupported` |
| `requestId` | UUID | **required** in this contract (the atomic confirm needs the claim) |
| `expected_owner` | UUID string | **required**; must equal the signed-in user id, else 409 `chat_owner_mismatch` |
| `context_scope` | `"conversation_only"` \| `"personalized"` | **required**. Request may only narrow the session's scope |
| `expected_privacy_revision` | integer >= 1 \| null | **required when `personalized`**; compared to the server revision |
| `support_session_id` | UUID \| null | optional. Attach the session to the conversation BEFORE the first send |
| `selected_intent` | `ground_present_v1` \| `untangle_thought_v1` \| `choose_step_v1` \| null | matching only (enables `selected_intent` reason) |
| `selected_memory_ids` | UUID[] (max 5) | references to the person's own saved memories; text is never accepted. Needs `personalized` |

Client input never carries memory text, instructions, activity results, provider/model choice, or a URL.

Effective scope: `personalized` only when requested AND the session allows it AND the account privacy mode is
`standard`. Otherwise the server answers with `conversation_only` and says so (`support.scope_narrowed_by`).
A `personalized` request against a `conversation_only` session is refused (409), never widened.

## 3. Success response (HTTP 200) - a superset of the legacy body

```jsonc
{
  "userMessage":      {"id":"<requestId>","role":"user","content":"...","createdAt":1793966400.0,"blocked":false},
  "assistantMessage": {"id":"<server uuid>","role":"assistant","content":"...","createdAt":1793966400.0,"blocked":false,
                       "contentOrigin":"model"|"interface_fallback"|"safety_response",
                       "isInterfaceGuidance":false},
  "message":          { /* identical to assistantMessage: legacy alias */ },
  "userMessageId":    "<requestId>",
  "quotaUsed":1, "quotaLimit":5,             // omitted for a safety response (no quota debited)
  "conversationTitle":null,                  // always null here: no title call
  "memoryUsed":true, "memoryIdsUsed":["<saved memory id>"],   // derived from the receipt, see below
  "coachData":null,                          // always null on this contract (no inline coach)
  "isCrisisResponse":true,                   // ONLY for a safety response
  "support": {
    "schema_version":1,
    "request_id":"<requestId>", "support_session_id":"<uuid>|null", "conversation_id":"<uuid>",
    "scope":"conversation_only"|"personalized",        // effective scope actually used
    "scope_narrowed_by":null|"account_privacy_mode",
    "privacy_revision":7,
    "content_origin":"model"|"interface_fallback"|"safety_response",
    "status":"completed"|"refused"|"safety",
    "suppress_ordinary_cards":false,                   // true for refused/safety: show no recommendation/upsell card
    "confirmed":true,                                  // true only after the database committed
    "persistence":"confirmed",                         // confirmed | saved_without_receipt | pending_reconcile (section 3.2)
    "context_receipt": {                               // null only for a safety response saved by the database fallback
      "schema_version":1, "receipt_id":"<uuid>", "request_id":"...", "support_session_id":"...|null",
      "conversation_id":"...", "assistant_message_id":"<uuid>", "privacy_revision":7, "scope":"...",
      "provider":{"vendor":"openai","model":"gpt-6-luna","route_version":"responses-chat-1"},
      "sources":[{"kind":"safety_policy|session|companion_memory|daily_intent|activity_result|message","id":"<uuid>","revision":0,"date":"ISO|null"}],
      "exclusions":["absence_metadata","health_data","inferred_affect","other_conversations","private_vault", "..."],
      "created_at":"ISO"
    },
    "proposal": null | {
      "id":"<server uuid = support-session proposal_id>", "template_key":"ground_present_v1|untangle_thought_v1|choose_step_v1",
      "reason_code":"current_request|approved_preference|selected_intent|general_option",
      "basis_kind":"companion_memory|message|activity|null", "basis_ref":"<uuid>|null",
      "suggested_step":"<<=400 chars, editable draft>|null", "status":"offered", "expires_at":"ISO"
    },
    "proposal_dropped": null | "invalid_proposal" | "template_declined" | "no_session" | "rejected_at_confirm"
  }
}
```

Rules the UI must follow:

- **A card exists only if `support.confirmed == true && support.proposal != null`.** Streamed text is provisional;
  no event before the terminal one carries a card.
- `content_origin == "interface_fallback"` (tool-only answer): `assistantMessage.content` is app guidance
  ("App option: Try a short grounding activity, or keep talking."), NOT something the model said. Render it as
  interface text (`isInterfaceGuidance`), never as a quote or as the person's/assistant's claim. The server also
  excludes it from later model history.
- `status == "refused"`: the text is the model's refusal; no ordinary card, no recommendation, no upsell.
- `status == "safety"`: the existing crisis response (`isCrisisResponse` true, `blocked` true). No model, no card.
  `provider` is `{"vendor":"none","model":"safety_response","route_version":"1"}`. Exactly one of three persistence
  states applies (section 3.2); always show the help text.
- `proposal_dropped` explains an absent card with a closed vocabulary; an invalid/duplicate/oversize/unknown tool
  never causes a second paid request. Offer the manual chooser instead.
- `memoryUsed` = receipt contains a saved memory or daily intent. `memoryIdsUsed` = the `companion_memory` source ids.
  `context_receipt.sources` is the complete disclosure ("shared with this reply", not "the model relied on it").
- `createdAt` (messages) and `context_receipt.created_at` are the handler's time at confirmation, stored once; they are
  within milliseconds of the database row. `proposal.expires_at` = that time + 24 h, a slightly early (conservative)
  display hint. The database enforces expiry and the revision at `accept_proposal`. For the exact stored receipt (with
  current ownership/deletion state per source) call `support-session` `{"op":"receipt","request_id":...}`.
- `basis_ref` is only ever a source id from this receipt (a saved-memory id); anything else was downgraded to
  `general_option` on the server.

### 3.1 Streaming (`Accept: text/event-stream`)

Events are `data: <json>\n\n`:

```
{"type":"delta","text":"..."}                        // provisional text only; never a card
{"type":"result","status":200,"data":{...above...}}  // terminal success
{"type":"error","status":409,"data":{...failure...}} // terminal failure after text started
```

If no text delta was produced (tool-only answer, or a failure before any text), the server returns a plain
`application/json` response with the normal HTTP status instead of an event stream. The client must accept both.
Text already shown is incomplete until the `result` event; on `error` discard it.

### 3.2 Safety reply: the three persistence states (`support.persistence`)

The fixed crisis help is always returned immediately with HTTP 200, but it is **never saved twice** and a reply whose
commit is unknown is **never reported as saved**.

| `persistence` | meaning | `confirmed` | `context_receipt` | `assistantMessage.id` | what the client does |
|---|---|---|---|---|---|
| `confirmed` | atomic confirm committed (now, or found already committed on this request id) | true | present | database id | normal |
| `saved_without_receipt` | the confirm contract is definitely absent or the database definitely refused; the one direct insert (origin and session recorded in that same statement) came back with a valid acknowledgment | false | `null` | database id | show it; no receipt available |
| `pending_reconcile` | commit state UNKNOWN after bounded idempotent attempts and a claim read (or, for the direct save, ANY outcome other than a valid acknowledgment: no second insert is ever attempted) | false | `null` | **placeholder** (deterministic from `requestId`, not a database row) | show the help now; keep the request id; do NOT resend as a new request; reconcile |

For `pending_reconcile`:

- Nothing further was appended and nothing was written over the request claim, so a late commit can still land. The
  placeholder id is stable for the request (`isInterfaceGuidance` false, `blocked` true) and is replaced, not merged, by
  the database id once known.
- Reconcile by re-POSTing the **same** `requestId` + content: 409 pending until the commit lands, then the stored
  confirmed response (`persistence:"confirmed"`, real ids). `support-session` `receipt` shows `NOT_FOUND` until then.
- If it never lands, the person still saw the help text locally; the user message itself was saved before this step.
  The server does not append a second reply under a different id to "make up" for it.
- A definite refusal after an earlier unknown attempt is treated as unknown (the earlier attempt may still commit).

## 4. Replay and reconciliation (same `requestId`, same content, same conversation)

- A confirmed turn: re-POST returns **the same JSON** (every id identical, same HTTP status) with zero provider,
  quota, budget or confirm work. The body is a pure function of the response stored by `support_confirm_chat_turn`.
- Different content/conversation under the same id: 409 `Request identifier already used`.
- In flight, or commit state unknown: 409 `"Request outcome pending. Reload history before sending again."`
  (`ChatRequestFailure.Kind.pending`). Poll the same request id; do not mint a new one.
- Ambiguous confirm: the server makes up to 3 attempts at the idempotent confirm (8 s each, same arguments), then **reads
  the canonical claim**. If a commit whose every response was lost is found, it is returned verbatim (same ids, `200`).
  Only if the claim is still pending does it answer 503 `chat_request_unconfirmed` (`retryable:false`) and write
  **nothing** over the claim, so a late commit is later returned by the replay above. `support-session` `receipt`
  returns `NOT_FOUND` until committed. (A safety reply returns local help instead of 503; see 3.2.)
- A stored failure replays as that failure. Only `retryable:true` failures accept `retryFailed:true` (one explicit retry,
  one more provider call, one more quota debit; the saved user message is reused).

## 5. Failures

All failures are JSON `{error, message, code, support_code?, retryable, ...}`. After the claim they also carry
`requestId`, `failureId`, `messageSaved`, `userMessageId` (existing `failedChatResponse`). **Pre-claim** failures store
nothing and may simply be re-sent under the same id once fixed.

| HTTP | `code` | when | `retryable` | extra / client action |
|---|---|---|---|---|
| 400 | `chat_support_schema_unsupported` | `schema_version` != 1 | false | pre-claim |
| 400 | `chat_support_invalid_request` | bad/missing new field, missing `requestId` | false | pre-claim |
| 409 | `chat_owner_mismatch` | `expected_owner` != signed-in user | false | pre-claim; drop the request (account changed) |
| 409 | `chat_privacy_revision_stale` | revision/source changed before dispatch, before confirm, or at the atomic confirm (new contract AND installed-schema legacy turns) | **true** | `current_privacy_revision`, `reason` (`privacy_revision`\|`source_changed`); refresh context, then `retryFailed:true` with the new `expected_privacy_revision`. Reply text is discarded, never published |
| 404 | `chat_support_session_not_found` | session missing/deleted/not yours | false | `support_code:"NOT_FOUND"` |
| 409 | `chat_support_session_mismatch` | session attached to another conversation | false | |
| 409 | `chat_support_scope_mismatch` | `personalized` against a conversation-only session | false | |
| 409 | `chat_support_session_closed` | session closed | false | start a new session |
| 413 | `chat_context_too_large` | required context cannot fit 128,000 bytes | false | shorter message / narrower scope; nothing sent |
| 503 | `chat_support_unavailable` | support contract not deployed/insufficient/transient (checked after the crisis check) | only `capability:"unavailable"` | `capability` = `not_deployed`\|`unavailable`\|`insufficient`; no spend, no old personal context |
| 503 | `chat_context_unavailable` | context sources unreadable (new contract, and legacy-shaped requests once the support schema is installed) | true | nothing read, sent or debited; explicit `retryFailed:true` under the same id |
| 503 | `chat_provider_unavailable` | provider incomplete/failed/empty/HTTP error | true | existing behavior; text and tool output discarded |
| 503 | `chat_confirm_unavailable` | confirm failed definitively (rolled back) | true | nothing saved |
| 409 | `chat_support_state_changed` | confirm refused (`support_code` from the RPC) | false | |
| 503 | `chat_request_unconfirmed` | commit state unknown, or transport lost | false | reload history / replay (section 4) |
| 429/503 | `chat_rate_limited`, `chat_quota_exhausted`, `chat_shared_budget_*` | unchanged | unchanged | unchanged |

## 6. What the server does and does not do on this contract

Does: authenticate; check `expected_owner`; check conversation ownership; claim `(user, requestId)` with the content hash
before anything else; build the context only from server-loaded, owner-scoped sources with `support-context-policy.ts`
(scope, suppression, revision, 20 messages / 64,000 history bytes / 48,000 memory bytes / 8,000 session bytes, whole
prompt <= 128,000 bytes including the fixed instructions, tool declaration and framing); revalidate privacy and sources
before quota debit and again before confirm; make exactly one Responses call (`gpt-6-luna`, `store:false`,
`max_output_tokens:500`, one strict `propose_support_action`, `parallel_tool_calls:false`); validate the raw tool
arguments; commit message + receipt + proposal + terminal response in one database transaction.

Does not: read `memory_fragments`, `companion_memory`, `daily_intents` or `profiles.last_absence_days` directly; add
re-engagement text; generate a title; extract memories; run the distortion coach; update memory usage stats; start,
complete or schedule anything; fall back to the old policy for any reason.

Safety (crisis keyword) turns use the unchanged detector, consented therapist alerts, and no quota/budget/provider.
They are attempted through the same atomic confirm (origin `safety_response`). Persistence outcome: section 3.2.

## 7. Legacy-shaped requests (installed clients that send none of the new fields)

Request and response shapes, `generateChatText` (no tool), 500 tokens, quota, budget, claim, receipts, error codes and
routing are unchanged. What changed is where personal context comes from and how the reply is saved:

| support schema | behavior |
|---|---|
| genuinely absent (`support_capabilities` missing, or it reports no context policy) | old baseline, byte-for-byte: direct reads of history, generated fragments, curated memory, daily intent, absence, and the old direct assistant insert |
| installed | NO direct reads of `memory_fragments`, `companion_memory`, `daily_intents` or the `messages` history. Memory, intent and history come from `support_context_sources` through the shared policy: Stop using, Forget, deleted, source-message / source-conversation suppression, expiry, life-context review, derived assistant turns, non-model (interface/safety) text, and a suppressed conversation are excluded. Generated fragments (pending, legacy_review, promoted) are never sent. Privacy mode on still means no personal context at all |
| installed but unreadable (capability probe or loader error) | fail closed: 503 `chat_context_unavailable`, `retryable:true`, nothing read, sent or debited; stored as a normal failure receipt (explicit `retryFailed`) |

Installed-schema legacy turns use the same privacy/source authority as the new contract, with the old wire:

1. The snapshot (privacy revision plus every cited memory, daily intent and history message with its version) is
   **revalidated immediately before the quota debit and provider call** and **again before the final save**. A correction
   accepted in between returns `409 chat_privacy_revision_stale` (`retryable:true`, stored as a retryable failure receipt;
   old clients map it through status + `retryable`). Before dispatch nothing is debited or sent; after the provider the
   reply is discarded; there is never a second provider call.
2. The final save is the atomic `support_confirm_chat_turn` with **`support_session_id: null`** (no session or history is
   invented for an old client; the context receipt allows a NULL session), `scope` `personalized` when privacy mode is
   off else `conversation_only`, `content_origin:"model"`, route `responses-legacy-1`, and the cited sources. The SQL
   re-validates them under lock and is the final authority. The stored response is the **legacy-shaped body**
   (no `support` block; `message` equals `assistantMessage`; `coachData` computed before the save is part of it), so a
   replay returns the identical JSON with the database message id.
3. Unknown commit outcome: the same bounded idempotent attempts and claim read as the new contract; otherwise
   `503 chat_request_unconfirmed` and nothing is written over the claim. No direct assistant insert ever follows.
4. A very old client that sends no `requestId` gets a server-generated claim for the same atomic path (it is never
   returned to the client).
5. Title, memory extraction and usage updates run only after a confirmed save. Extraction rechecks the privacy revision and
   suppressions before the provider call and again before storing a candidate.

Unchanged for privacy-off legacy requests where it is still eligible: re-engagement (absence) context and the
`memoryUsed`/`memoryIdsUsed` fields (now the eligible curated ids).

Legacy crisis replies: the fixed help text is saved with exactly **one** insert, and that insert never has an untagged
retry. Which insert it is depends on what is known about the schema:

| schema knowledge | the one insert | outcomes |
|---|---|---|
| installed, or merely unknown (capability probe unavailable) | carries `content_origin:"safety_response"` (and `support_session_id` for a new-contract request) in the same statement | a **valid acknowledgment** (see below) = saved; **every other outcome = pending** |
| known absent (the probe says the function does not exist) | the old untagged insert, untouched | valid acknowledgment = saved; a server-reported failure is the old hard error (HTTP 500); a response that reports no error but carries no valid acknowledgment = pending |

- A rejection never unlocks a second insert. PostgREST `PGRST204` (schema-cache miss) and PostgreSQL `42703` mean the
  cache or statement refused a column; they do **not** prove the column is absent. A stale cache can refuse
  `content_origin` or `support_session_id` while the database has both, and an untagged retry would then store a
  NULL origin that later reads as model text. So a refused column, a constraint violation that names the column,
  transport loss and a lost response after commit are all **pending**.
- **Valid acknowledgment:** the inserted row comes back as an object with a canonical UUID string `id`, `role` equal to
  `assistant` and the request's `conversation_id`. `{}`, an array, a numeric `id`, a row for another conversation or role
  are not acknowledgments, whether or not the row actually committed. Nothing is retried and the claim is never completed
  from an unacknowledged save.
- **Pending response:** HTTP 200 with the fixed help text and the legacy shape (`isCrisisResponse:true`;
  `assistantMessage.id` is a stable placeholder derived from `requestId`, not a database row; no `support` block for a
  legacy-shaped request; a new-contract request gets `support.persistence:"pending_reconcile"`). The request claim is left
  pending, so a replay answers 409. A row that did commit is already tagged, so later model turns never receive the text as
  history; a row that did not commit leaves nothing for them to receive.
- Help never depends on a provider, quota, or any of this.

## 8. Cited history messages: the integration contract with the M3 SQL

Server-owned `messages.content_revision` (0 default; bumped by the database only when `content`, `role`,
`conversation_id` or `content_origin` really changes; an in-place rewrite such as `apply-rewrite` bumps it but not the
privacy revision):

1. `support_context_sources.history[].content_revision` -> policy `HistorySourceRecord.revision` -> the receipt source
   `{kind:"message", id, revision}` (this is what the response and the stored receipt cite).
2. Before the quota debit and again before confirm, this helper looks up **each cited id exactly** (not the latest-N
   window) and requires: it exists, is in this conversation, same role, model origin, same dispatched text (user text
   compared after the same sanitization), the same revision, and is not suppressed. Anything else is
   `409 chat_privacy_revision_stale` (`reason:"source_changed"`, retryable); before dispatch nothing is spent, after the
   provider nothing is confirmed, and there is never a second provider call. New messages that merely push a cited one out
   of the latest window are NOT staleness.
3. `support_confirm_chat_turn` is the final authority: under a share lock each cited message must exist in the request's
   conversation at exactly the cited revision (omitted means 0), else `PRIVACY_REVISION_STALE` (`source_changed:message`).
   `accept_proposal` re-checks a message basis against the revision its request cited.
4. Version skew: a policy that does not cite revisions (older TypeScript) against a schema that has bumped one reads as
   a stale source on every edited message. Deploy the policy and this helper together with the migration.

## 9. Logging and error text

Logs and ordinary error bodies are content-free: event names, HTTP status, request ids, database error CODES (never
messages) and a small fixed set of categories (`invalid_json`, `transport`, `aborted`, `timeout`, `http_response`,
`unexpected`, or this codebase's own constant codes such as `AI_HTTP_503`). Provider response bodies, error messages,
database error objects, stacks, session configuration and any message/memory text are never logged or returned. This
includes the distortion-coach helper (`_shared/reframe-templates.ts`), which now logs a database code or `exception` only.
